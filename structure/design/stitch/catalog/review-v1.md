## 7. Backend Capability Alignment

### Filter architecture

All three generated designs use `<input type="radio">` for all filter parameters — single-select per parameter group. This aligns with the backend `params.{key}=value` exact-match filter that supports only one value per parameter key.

No `<input type="checkbox">` multi-select filters appear in any theme. No price range sliders. No faceted product counts (e.g., "32 GB (6)"). These are correctly absent.

### Filter value mismatches (require implementation correction)

| Theme | Parameter | Generated `value` attribute | Backend stored value | Action required |
|-------|-----------|---------------------------|---------------------|----------------|
| All | RAM | `"16 GB"`, `"32 GB"`, `"64 GB"` | `"16"`, `"32"`, `"64"` | Strip unit suffix — use raw numeric string |
| Professional | GPU | `"RTX 4070"`, `"RTX 4080"` | `"NVIDIA RTX 4070"`, `"NVIDIA RTX 4080"` | Add "NVIDIA " prefix — use full backend value |
| Professional | CPU (some) | `"Ryzen 9"`, `"Intel i9"`, `"Intel i7"` | `"AMD Ryzen 9 7945HX"`, `"Intel Core i9-13900HX"`, `"Intel Core i7-13700H"` | Use full model names from API |
| Premium, Gaming | GPU | `value="NVIDIA RTX 4080"` | `"NVIDIA RTX 4080"` | Correct — no action needed |

**Key rule:** At implementation, filter values must come from `GET /api/categories/:id/parameters/:key/values`. Do not use `value` attributes from Stitch-generated HTML as the source of truth.

### Screen Size parameter

The Gaming Laptop category has 5 parameters including `screen_size` (NUMBER). None of the three generated Stitch designs show a Screen Size filter group. This is expected — the prompt did not include Screen Size to keep the demo clean. At implementation, the filter panel must render all parameters from the API dynamically, including Screen Size.

### Pagination backend contract

The backend returns `{ products: [...], meta: { total, page, limit, totalPages } }`. The CatalogPage pagination behavior must implement:

| State | Behavior |
|-------|---------|
| `totalPages > 1` | Previous enabled on pages > 1; Next enabled on pages < totalPages |
| `totalPages === 1` | Both Previous and Next disabled (matches V1 mockup state) |
| `total === 0` | Pagination hidden; "0 Gaming Laptops" result count; empty state message shown |

## 9. Implementation Recommendations

### Component architecture

The CatalogPage shares the following components with the HomePage and should use the same implementations:

- `<Header>` — identical structure; `activePage="laptops"` prop needed for Laptops active state
- `<Footer>` — identical to HomePage (Gaming, Professional); Premium footer may differ
- `<ThemeSwitcher>` — same dropdown component, same Zustand `themeStore`
- `<ProductCard>` — extend existing ProductCard with 2–3 badge variants; Professional gets optional CPU badge
- `<CartBadge>` — reuse from HomePage

New components needed for CatalogPage only:

- `<FilterSidebar>` — dynamic parameter rendering; radio group per parameter
- `<ActiveFilterChip>` — theme-specific pill or rectangular chip with remove button
- `<CategoryNav>` — sub-navigation within Laptops category
- `<SortBar>` — result count + sort dropdown
- `<Pagination>` — Previous/Next with page numbers

### Filter state management

Filter state (`params.{key}=value` entries) should live in URL query params or Zustand `filterStore` to support:
- Preserving filters when switching themes
- Back-button navigation
- Shareable filtered URLs

Theme switching must NOT clear filter state.

### API integration sequence

```
1. GET /api/categories/{categoryId}  → category metadata, parameters[]
2. For each parameter: GET /api/categories/{categoryId}/parameters/{key}/values → available filter values
3. GET /api/products?categoryId={id}&params.ram=32&sort=price-desc&page=1 → products + meta
```

Render filter groups from step 1–2 results, not from hardcoded Stitch HTML values.
